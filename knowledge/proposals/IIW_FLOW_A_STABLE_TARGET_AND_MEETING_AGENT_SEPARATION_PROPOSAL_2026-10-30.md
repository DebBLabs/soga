# IIW Flow A Stable Target and Meeting-Agent Separation Proposal

Date: 2026-10-30  
Status: PROPOSED — PENDING BLIND DUAL REVIEW AND PI ACCEPTANCE  
Scope: IIW table presentation design and separate supervised meeting use of the agent team

## 1. Purpose

Freeze one clear public-table experience without repeatedly rewriting visitor-facing
screens as internal implementation work advances.

The IIW table will present only the Permission to Speak path (Flow A). The live
multi-agent explanation experience will move to selected, PI-supervised meetings and
will not be part of the table build, Beryl runtime, QR flow or robot path.

This proposal records a stable-target presentation rule:

- the visitor-facing UI describes the target interaction the team is working to make
  operational for IIW;
- internal records continue to distinguish target, implemented, executed and accepted
  capability;
- the UI is not repeatedly rewritten merely because an internal sprint is incomplete;
- if a target capability will not be ready for public use, the PI will directly approve
  the truthful fallback wording before the public rehearsal or event.

## 3. PI-selected public-table boundary

### 3.1 Single public path

The public IIW table has one visitor path: **Permission to Speak**.

Remove from the table presentation:

- the Project Agent landing card and QR;
- the table-facing Project Agent screens and route;
- two-path explanatory copy and layout;
- any suggestion that a public AI session participates in authorization.

The landing screen becomes a single centered Permission to Speak entry. Associated
labels become singular:

- `Choose one of two paths` / `Choose paths` become start-oriented wording;
- `Each QR starts a different experience` becomes one-path introduction copy;
- `Return to both paths` becomes `Return to start`;
- camera guidance refers to the single table QR.

These are the only PI-approved editorial changes inside the locked navigation shell.

### 3.2 Locked Flow A

The five Flow A stages and its decline branch are locked as the target design. No
editorial, visual, behavioral or navigation change is permitted without new direct PI
approval.

The locked target includes:

1. the farmers-market moment and the governed-interaction comparison;
2. one short-lived encounter and the AAuth/SOGA permission boundary;
3. the adult's Allow or Decline branch;
4. on Allow, permission for the robot to ask—not permission to compel participation;
5. a five-second natural-response window;
6. on a clear yes, one bounded dance and a closed interaction;
7. on decline, no question, speech, movement or dance;
8. on no, no clear response or stop, no dance;
9. the final laptop roadmap and a closed phone interaction.

The final public build must preserve the PI-approved meaning and flow. Mechanical
layout work may implement the design but may not silently rewrite it.

## 4. Stable-target and truthful-state rule

The table UI is a target experience, not a sprint-status dashboard. Internal state is
tracked in proposals, decisions, tests, evidence and the operator checklist.

Before public rehearsal, the integrator must produce a target-readiness reconciliation
for every visitor-visible capability. Each item is classified internally as:

- implemented and accepted;
- implemented but pending evidence;
- not implemented; or
- removed from the event plan by direct PI decision.

The UI remains stable while work is progressing. At the public-rehearsal holdpoint,
every visitor-visible capability not classified `implemented and accepted` must have
either PI-approved, independently reviewed fallback wording or a PI decision removing
it from the event. Otherwise the rehearsal does not proceed. No agent or reviewer may
silently change the target UI or waive this holdpoint.

Every visitor-visible state report must be driven by actual runtime state and record the
source of that state. No scripted or timed progression may claim that an event occurred
when it did not. The readiness reconciliation must name the source for:

- encounter active;
- invitation permitted;
- response window open;
- clear yes, clear no, timeout and adult withdrawal;
- bounded movement complete; and
- interaction closed.

For the IIW role-play, the source of clear yes, clear no and timeout must be explicitly
classified as sensor-derived, operator-observed, adult-entered role-play input or not
implemented. The public UI and operator script must not imply child sensing when the
state actually comes from an operator or adult fixture.

Two claims require explicit reconciliation before public rehearsal:

- the exact AAuth/SOGA sequence shown on the protocol screen must be checked against
  the pinned AAuth editor source at commit
  `fcf656de1926535f5bd6fc0538147ead6646e727`, protocol SHA-256
  `295ba2a0edd99dd077c4c877b6276608000419fdf4bbef2327da0c6e4d950953`,
  and the accepted presentation implementation—not revised from reviewer memory or
  inference. The integrator must record the reconciliation as a written artifact for
  blind dual review. A confirmed mismatch requires PI-approved, independently reviewed
  corrected wording or a PI decision labelling the screen illustrative before public
  rehearsal;
- mBot2/CyberPi speech, the five-second response handling and bounded movement must be
  integrated under a separately reviewed proposal and evidenced, or the PI must approve
  independently reviewed truthful fallback wording.

## 5. Separate supervised meeting-agent track

The agent-team experience is not part of the IIW table build. It may be prepared for
selected meetings under a separate proposal and authorization.

Its intended purpose is to make the project method visible: a visitor asks a real
question; Codex, Claude and Gemini answer independently from the same public-only
briefing; each may identify one next question; the PI selects any follow-up.

Minimum controls for any later meeting authorization:

1. Debbie supervises and controls every interaction and display decision.
2. The public briefing is frozen, hash-pinned, checked for held-in-trust or private
   content, and differs between agents only in the disclosed role line.
3. Dedicated public-only profiles or sessions have memory, personalization, custom
   instructions, projects, tools, connectors, repository access, file access, browsing
   and code execution confirmed off.
4. Visitor questions are relayed by Debbie or an operator; visitors are told that the
   question is sent to three third-party AI services, may be shown to the room, and must
   contain no names or personal data.
5. All three answers are collected before any is displayed. No answer is shown to
   another agent unless the PI expressly chooses to do so and discloses it.
6. Answers are short, labeled by model, labeled AI-generated and potentially wrong,
   and subordinate to Debbie's statements.
7. Each agent may produce at most one next-question. The PI selects at most one
   follow-up round. There is no automatic or recursive agent-to-agent loop.
8. The agents explain the work only. They receive no authority over the table, Beryl,
   AAuth/SOGA decisions, a robot or any external action.
9. The meeting device and network remain separate from Beryl and the private demo
   runtime.
10. Provider training and data-sharing controls are disabled where available.
11. Any public log omits visitor identity and does not retain exact visitor wording
    without explicit permission.

This proposal does not authorize a meeting session, agent execution or preparation of
the public briefing. Those require a later independently reviewed proposal.

## 7. Holdpoints and exclusions

Acceptance of this proposal grants only the bounded, uncommitted file updates in
Section 6. It grants no:

- commit, push, import, compilation, lint, test or execution;
- listener, browser execution, Beryl access or router change;
- QR generation, printing or scan;
- iPad provisioning or other device contact;
- live meeting-agent session, model query or public-briefing preparation;
- Project Agent execution;
- mBot2, CyberPi, Misty, robot, sensor, speech or movement work;
- SOGA source modification;
- Phase B, G28 or G29 progression.

The unrelated PI routine-tool-approval proposal remains excluded, unread and
untouched.

After bounded implementation, all of these holdpoints apply in order:

1. The complete changed-file list, exact SHA-256 hashes, runtime-source mapping and
   string-by-string Flow A comparison receive blind dual static review.
2. The PI accepts the exact reviewed static package before commit or execution.
3. The accepted presentation hashes and runtime manifest are re-pinned.
4. A separately reviewed controller runs the complete bounded test suite once and
   writes durable evidence; no automatic retry.
5. The resulting evidence receives blind dual review and PI acceptance.
6. A fresh Phase A laptop-only visual preview is separately proposed, reviewed and
   authorized because D-174's visual acceptance covered the superseded two-path table.
7. The PI visually accepts the single-path landing and every Flow A branch.
8. The integrator's written target-readiness reconciliation, including the pinned
   AAuth/SOGA comparison and every visitor-visible runtime-state source, receives blind
   dual review and PI disposition.
9. The PI confirms that every embedded real photograph contains no identifiable
   bystander, especially a child, before public display.
10. Phase B remains blocked until all preceding holdpoints pass and a separate Phase B
    authorization is independently reviewed and accepted.

At the public-rehearsal holdpoint, any visitor-visible capability not implemented and
accepted must have PI-approved, independently reviewed fallback wording or be removed
by PI decision. Otherwise rehearsal stops fail-closed.
